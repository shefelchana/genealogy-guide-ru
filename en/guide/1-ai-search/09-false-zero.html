The false zero: when the tool was wrong, not the source

What this section covers: what to check when a search returns zero, before you write "none". Why a site looks unavailable, how a zero comes from a wrongly assembled query, where the control record ends, how to count the gap between spellings, how to query an archive catalogue, and why a mark in a database may not be about your person. Sections 15–24 are about how the server itself goes wrong: an empty answer through a failure, invisible characters in titles, results pages, response codes. Sections 25–31 are about errors of reading and of the negative conclusion: the index, the list of forms, OCR, directories, the chain of reports, the extract. Sections 35–38 are about a false zero hidden behind non-empty results and behind an address: a homonym in a place name, the number in a card's address, an image folder, a separate host for images.

Sections 1–24 were written from two contributions sent by one reader of the guide (October 2026), and sections 35–38 and the labelled additions in sections 5, 9, 12, 25 and 32 from his third contribution (November 2026); all under the CC BY 4.0 licence. Sections 25–31 and the additions at the end of sections 7 and 11 come from the compiler's own research with a team of agents (October 2026) and carry no label; "the author" in sections 1–24 is the reader who sent the material.

The label [reader's experience] means: the author of the contribution did this and checked it on live queries (September–November 2026, their own project), and the compiler of the guide did not repeat those queries. The figures belong to one project, sites may have changed since — check yourself before an important conclusion. The other labels are explained in the Glossary.

The main point: "the record does not exist" and "I did not find it" are different statements, and the second is far more common. Before closing a direction, separately make sure that the instrument is in working order: the site, the query address, the search mode, the route. The general conditions of a negative conclusion (coverage, spellings, method, control record, date of search) are in Standard of proof, section 7. Here is what is added to them.

1. "The site is unavailable": six diagnoses

The page did not open, but the causes differ. "Come back later" applies only to the first three.

Diagnosis Sign What to do
The site's name is not found (DNS) the browser does not know such an address wait, check from another network
Connection refused "connection refused" wait; check whether the site works only over http (below)
Certificate a TLS error, the browser warns of danger wait; whether to open it is for the human to decide
Bot protection 403, a Cloudflare stub, a CAPTCHA the human opens it themselves in an ordinary browser
A refusal to the program specifically 403 to a script or agent, while everything opens in an ordinary browser the site is alive, a zero from it is not a result; work in a browser
The resource has changed the site works, but the section, database or function is no longer there re-read the site afresh: the notes about it in your files are out of date

One more case — a block by country or because of a VPN — is covered in Access, CAPTCHAs, pace, section 4. The same page has the list of sites that closed or changed in 2026.

Details [reader's experience]:

  • A refusal to a program. The site of the Jewish community of Lithuania answered 403 to every automatic request and for three weeks stood in the author's notes as "dead", though it opened in a browser. The diagnosis: only your program gets 403, while in a browser the page opens — the site is alive, and a zero from it is not a result. What to do: open the page yourself in an ordinary browser or through an AI plugin in the browser. Do not disguise a program as a browser if the site's rules do not allow automatic access. On a CAPTCHA or a robot check — stop: from there a human acts (Access, CAPTCHAs, pace, section 3).
  • A site without HTTPS. A tool that itself rewrites http to https gets a connection refusal, and it looks like "the archive is down". A South African catalogue of 8.3 million records opened only strictly over http.
  • 403 for the whole domain, including /robots.txt, is a server protection, not the absence of a page. In the log write "blocked", not "none".
  • A link from someone else's database leads by an old address scheme. In one name database the "image" button led by an address scheme the archive had long abandoned. There is no 404 error: the link silently takes you to the archive's home page, and this is easy to take for "no image". If a link from an index brought you to the wrong place, look for the file by its archival reference on the archive's current site and do not write "not digitised".

2. The instrument too has a shelf life

That a negative result is valid only as of the date of the search is stated in Standard of proof, section 7: databases grow. The second half of the rule: the instrument itself changes. In a single day the author removed six false zeros, and two of them were about a resource, not about people. One site had put up a login, and "a zero from it" had since meant a zero from one database among many. On another, the text search had been switched off. The notes about them in the project files stayed the same [reader's experience].

→ When you repeat a search on old resources, check at the same time that the resource is still the same: the same access, the same databases, the same kind of search. In the research log keep next to a zero the date and what the instrument was like.

3. A zero from an address assembled by hand

AI (and a human too) often builds a query address itself: it puts parameters into a link or an API. A wrong parameter name gives not an error but "nothing found".

Examples [reader's experience]:

  • in the Yad Vashem API the field for the submitter's surname is named differently from the web form (submitter_ln_search_en versus submitter_ln). A field name from the form, put into the API, gave a silent zero on a whole series of queries;
  • the place parameters in the advanced search of the same resource did not work at all: a query for a shtetl that certainly exists gave zero. The sign is in the header of the results ("Search criteria"), which shows not what you asked for.

The opposite trap: a made-up filter parameter is silently skipped by the database, which returns everything it has — for the author 24 million records instead of a refusal [reader's experience]. A full list easily passes for the result of a search. Similar "quiet" failures of the JewishGen and USHMM forms are in Access, CAPTCHAs, pace, section 3, item 8.

→ Compare the number found with the total size of the database: if they match, the filter was not applied. And read what the database showed in the header of the results as your query.

🔑 A zero from an address assembled by hand proves only that the address was assembled that way. Take addresses from the pages of the site itself; how to demand this of an agent — Working with agents, section 4.

4. A control record — for each route

A control record (Standard of proof, section 7) tests the search itself. It has two limits [reader's experience]:

  • The same database opened another way is a different instrument. One collection through the general search and through the collection's own page gave different results; in the second case a zero came out even for a surname known to be common. Run the control record for each route separately.
  • A control by place tests the place, not the surname. In a "smart" search different spellings have different dictionaries of synonyms: KREEL pulls in KRELL, while KRIL pulls in nothing. A zero for one spelling with a confirmed place proves only that this spelling is absent. To close off a surname you need to go through the spellings with the same place.

5. Phonetic search also depends on the spelling

In Names, surnames, spellings (section 2) it is advised to begin with exact mode and add phonetic. The author's experience shows that phonetics does not cover everything either [reader's experience]:

  • Different sets. The JewishGen general search, the surname Рабичев (Rabichev): Rabichev phonetically — 355 records, Ryabichev by the same algorithm — 47. And this is not a subset of the first: the second result contains whole databases that are not in the first (Belarusian voter lists, a concentration-camp card file), and other households in the census.
  • The gap can be counted. The surname Пищик (Pishchik): Pishchik with synonyms — 111 records, literally — 107; Piszczyk — 1; together 108 of 111. Pischik, both with synonyms and literally, gives 10 — the remaining three do not fit in them. So at least seven records lie outside the earlier result, and the earlier note "all 111 viewed" was false. This is not a suspicion but a count.
  • It also happens the other way. In Yad Vashem the mode with synonyms gathers all the spellings known to the database into one set: nine forms of the surname Беленький (Belenky) give exactly 1,850 records each. But Belenkij, Byelenky, Belenkyi give zero even with synonyms — the database simply does not know them.

🔑 So before you go through spellings, find out what the search does: widens the query with synonyms or searches literally. Going through spellings means different things in these two cases:

  • in the literal one — so as to miss nothing;
  • in the synonym one — to find out which spellings the database knows at all: a spelling it does not know gives a false zero.

And within Cyrillic: in a part-of-word search in one catalogue "Беленк" and "Беленьк" found partly different things — the soft sign breaks the stem [reader's experience]. Try the stem both with "ь" and without.

Ukrainian archive catalogues normalise the unstressed vowel [reader's experience]. In one oblast archive's catalogue, in one index and within one minute (21.11.2026): Рабічев — 0, Робічев — 1. On the paper itself the surname is written in Russian, «Рабичевъ», but the catalogue's Ukrainian rendering went through "о". → In Ukrainian catalogues run both variants of the unstressed vowel in the root (о/а, е/и). This is cheaper than phonetic search and catches what phonetics misses: the forms sound the same but differ in letters.

6. Pairs of cursive letters that break a search by stem

Don't read Russian? See For English speakers.

To the pairs from Names, surnames, spellings, section 5 (Б/В, Ш/Т, Р/К, "-ель/-еръ"), the author adds: г/ч · н/п · и/н · л/м · я/и [reader's experience].

An example: the surname Велигура (Veligura) in the Omsk ZAGS books is written "Виличура". The stem "лигур" is not in this word, and a search by a truncated stem passes it by. This is a property not of one scribe but of a whole corpus: in another family and another uezd a record turned up, "Велигуров Величуров Иван Ильич" — two forms of one person in one line, and under one archival reference "Любава" and "Любовь" [reader's experience].

→ Found a form with "ч" — look for the form with "г", and vice versa.

7. Search by what the scribe could not distort

The surname is the longest and rarest word in a record, and it is spoiled first. The given name, patronymic, year and place of registration are shorter and more familiar: the scribe had heard them hundreds of times. For the author a family was found by a query without the surname — "all children of any Tikhon registered in such-and-such a settlement" — and the distorted surname surfaced in the results by itself [reader's experience].

The same technique for metrical records — write out the whole shtetl over a window of years and sort by the parents' names: Scenarios, B1, item 12.

Re-read a list checked by surname, this time by patronymic. In the compiler's research a man died in 1850 and had to appear in the revision (reviziya) of that same year, yet a search by surname "did not find" him. Re-read by patronymic in all its forms, and, where the list has a column "no. of the revision list", by that column too: the family number finds a person even when the surname is illegible. That is how, in one round, a man turned up whom an earlier pass by surname had missed.

8. An archive catalogue: ask with one word

On the catalogue of one oblast archive (the design is typical) [reader's experience]:

Query Answer
похозяйственные книги Называевск (household registers Nazyvayevsk) 0, "Nothing found"
Называевского района похозяйственные (of Nazyvayevsk district household) 0
похозяйственные (household) 6,644 files
Называевск (Nazyvayevsk) 4,161 files

The catalogue joins words with "AND" and looks for them in one file title. But files are titled "Household registers of the aul Ablay" (Похозяйственные книги аула Аблай): the document type and the district do not occur together in one title. A two-word query gives a guaranteed zero, however large the fond. This is the same case as in section 3: a zero proves only how the query was assembled.

→ Ask separately for the document type and separately for the place, and intersect the lists yourself.

In the same catalogue [reader's experience]:

  • a stem finds more than the full form: "Велигура" — 1 file, "Велигур" — 2; the second turned out to be a personal file with an autobiography;
  • a book can be selected whole by the file's reference, not by name: a query on the reference field (for the author of the form fields[9]=д. 1336,) returned all 492 records of the book. This removes the dependence on the "place of registration" column, which is filled in differently within one book;
  • one archive may have two search systems with different results: for the name of one village — 52 files in one and 37 in the other. These are different sets, not one with different paging.

9. The most reliable zero — when the source itself names the total

Before building an external check, see whether the source gives its own total. A metrical book closes a month with a line like "total male five" (итого мужескаго пола пять) with the rabbi's signature, a revision gives the number of souls per household, an inventory gives the number of storage units. If the total agreed with the number of records read, the list could not have been overlooked, and the zero for the surname is firm. Checking the numbering of records and households is in the reading-archive-scans skill, the section "Proof of completeness" (Доказательство полноты).

The arithmetic of the document itself can also decipher conventional marks [reader's experience]. In a list of parishioners of a prayer house for 1896 there were marks explained nowhere: a blue "V" and a red "Н". There were exactly 66 blue ones and 32 red ones, one line was struck out with the note "excluded on account of death" (за смертію исключенъ) — 99 living. In the minutes of a failed meeting on the neighbouring frame it says that attendance "makes up less than 2/3" (составляетъ менѣе 2/3), that is, a lawful meeting needs two thirds. Two thirds of 99 is exactly 66. The author's conclusion: V — "appeared" (явился), Н — "did not appear" (не явился). This is a conclusion from a converging count inside the file, not from analogy.

The limit of the rule: "a complete book" ≠ "complete registration" [reader's experience]. A signed total certifies the body of the book: five entries, no leaf torn out. It does not say that every birth of the month reached the rabbinate: with a late declaration, a birth while travelling, a circumcision at home without a declaration, no entry was made at all. What catches this is the density of entries against neighbouring years of the same book: if a shtetl has 49 births in 1884, 49 in 1893 and seven in 1888, the signature under 1888 is honest, but registration that year was incomplete, and a zero by surname for 1888 is weaker than for the years around it.

10. For every zero — a number and a denominator

A zero without the number viewed does not count as a result (see "coverage" in the Glossary). But a number without a denominator also says little [reader's experience]:

  • "106 records for the shtetl" is 19% of the shtetl if it has 551 households;
  • "our man is not among the 118 signatories" is 118 of 245 householders, 48%, and the direction is not closed.

→ Write in the research log: "viewed N of M (X%)" — and where M comes from.

11. One archive — two naming schemes on Commons

On Wikimedia Commons the files of one archive may be uploaded under two schemes of file names [reader's experience]:

  • the Ukrainian — ЦДІАК 1167-1-500 Метрична книга…;
  • the Russian — Фонд 1240 Опись 1 Дело 46 Метрическая книга….

A query in one scheme does not find the files of the other: ЦДІАК 1267 gave 0, Фонд 1267 — 49 files. According to the author, in the same place, after several fonds were merged into one (2020), some files lie on Commons twice — under the old and the new number, as different scans. How to find a file by its reference in all variants of the name — the ukrainian-archives-on-commons skill, step 3.

A fond's category can be incomplete too. In the compiler's research the marriage books of one rabbinate for seven years lay on Commons outside the category of their fond, and the earlier conclusion "there are no books for these years" turned out to be a false zero. Check coverage in two ways: by category and by searching file names (intitle: with the reference; the same step 3 of the skill).

12. A file's title is a statement, not a fact

A file is titled "Metrical book of the synagogue of the shtetl Chernobyl, births 1864–1879" (Метрическая книга синагоги м. Чернобыль о рождении 1864–1879), and in the inventory itself there is a note: "error in the inventory, correctly the shtetl Khabnoe" (ошибка в описи, правильно м. Хабное) [reader's experience]. Read the annotation and the archive's notes in the inventory. File captions on Commons are also sometimes false — the reading-archive-scans skill.

Three more observations alongside [reader's experience]:

  • a fond may be by society, not by shtetl: the metrical books of shtetl A lie in the fond of society B, to which it is registered. A family "of such-and-such society" lives now in one village, now in another, while its records are in one fond (on pripiska — Records of the Russian Empire and the USSR, section 4);
  • one shtetl may have two fonds — one per confession, with neighbouring numbers: it is easy to order the Catholic one instead of the Jewish;
  • a whole kind of record may be absent because of the fond's composition, not because of loss: for one shtetl after 1862 there are neither death books nor divorce books — only births and marriages. Before looking for a death, check in the inventory whether death books were kept in this fond at all. Otherwise a month goes on searching for what does not exist, and "not found" goes into the log. How to record such a gap — Standard of proof, section 7, "Gaps in the sources themselves".

The same goes for dates [reader's experience]. The cover of a file says «кончено: 29 июня (crossed out) / апреля 1916 г.» ("finished: 29 June / April 1916"), while the catalogue card says 29.06.1916: the compiler copied the crossed-out date. The reading "crossed out" was made by the reader's executor and he did not check it on the image himself, so the case is probable, not proven. The rule does not depend on it: a date in the card is a reading of the cover, not a fact about the file, and "catalogue against cover" is decided for the cover.

13. A mark in a database is a property of the collection, not a fact read

Indexers often put a status ("murdered", "killed") on a whole collection by its type, without reading each record. For the author five cards carried the mark "murdered", and the death was recorded as proved. The collection was called "List of murdered Jews from Yizkor books", while the memorial entry itself said nothing about a death. The people it commemorated died their own death overseas — one five months before the Germans arrived, as the date on the gravestone shows [reader's experience].

→ Before accepting a status, ask: was it read in a document or assigned to the whole collection? And check whether the source is able to distinguish: if neighbouring records directly write "died in such-and-such a town" and yours is silent, the silence does not mean what it seems.

14. A relative's story: what to believe

In two long interviews, for the author dates, addresses and family links were confirmed, but names were not [reader's experience]. The narrator remembers that "uncle lived on such-and-such a street and left before the war", and mixes up whether it was Aron or Aaron. Do not fit a find to the name from the story — check it by date and address.

With other narrators memory mixes up years too (Talking to relatives, section 5), so the general conclusion is more cautious: a name from a story is the least reliable field, and only a document confirms it.

15. One measurement is not yet a result: the server sometimes returns an empty answer

The signs of an honest zero from section 3 — code 200, the line "nothing found", your query echoed in the results header — check that the query was assembled correctly. They do not catch a failure of the server itself. For the author, one and the same query to a catalogue that always answers the same question the same way gave, seven times in a row, 2 · 0 · 2 · 2 · 2 · 2 · 2. The empty answer carried the query in the header and "nothing found", and its length in bytes did not differ from an honest one [reader's experience].

On this catalogue the author counted 8 empty answers in about 132 queries — about 6 %. If the failures are independent, the probability of getting a false zero in every measurement in a row is [reader's experience]:

Measurements Probability of a false zero
1 about 1 in 16
3 about 1 in 4,400
6 about 1 in 19 million

⚠️ The rate was measured on one catalogue over a few days: on another site it may be higher or lower. And the calculation assumes the failures are independent, while the author noticed that they cling to fast series of queries — that is, exactly to running through spellings. The more conscientiously you go through the spellings, the more likely one of the forms gets a false zero and goes into the log as "does not occur".

→ Repeat a zero on which a conclusion will rest with a pause, not back to back: the author's threshold is three measurements, six for an important conclusion. A support without repeats — section 18.

16. A word in a title can be broken by an invisible character

A long word in a file title is sometimes broken by a hyphenation, and the author searched for it in parts, going through the possible break points. This works if the break is an ordinary hyphen. On one catalogue the author tried the forms with a hyphen, got zero, and a control query confirmed that the search worked. But in the real titles the words were broken by a soft hyphen (U+00AD) — a character you cannot see on screen [reader's experience]:

Query Found
техниче + soft hyphen + ский 6
техниче-ский (ordinary hyphen) 0
технический ("technical") whole 47

These are different sets, and both are non-empty: the catalogue does not join words across a soft hyphen. In a full export for one uezd (district), 44 titles of 712 were broken this way — about 6 %. Such files drop out both from the results and from the "found: N" counter, so checking against the counter does not catch them [reader's experience].

→ Before building conclusions on zeros from a catalogue, save the raw response and count the soft hyphens (U+00AD) and the different hyphens (U+002D, U+2010, U+2011) in it. Any AI agent with access to files can do this.

The author's lesson about control: the control query worked, but it confirmed something other than what was being checked. A query for a known word checks that the search works. A guess about which character breaks a word is checked only by reading the real titles in the results.

17. A typo in the inventory itself: only a truncated stem helps

An export by the name of the uezd gave 712 files, by a truncated stem — 723. Of the 11 extra, 7 were noise (people with the same surname, another village), and 4 were real files of the same uezd: one broken by a soft hyphen (section 16), three written by the archivist with a missing letter — "Трубческий" instead of "Трубчевский" (Trubchevsk uezd) [reader's experience].

A missing letter in the inventory is found neither by trying hyphenations nor by grammatical cases — only by a search on a truncated stem. The cost is about 1 % noise; the gain is files the full word does not see. That a stem finds more than the full form is said in section 8 too; here is one more "why": it protects against a typo in the catalogue itself.

18. A zero for a piece of a word confirms the zero for the whole word

If the search finds a string inside a word (search by part of a word), the results for a long string are wholly contained in the results for any piece of it. So if ищик gives zero, then any surname ending in "-ищик" (-ishchik) must give zero too [reader's experience].

This is a second, independent support under a zero: one extra query instead of the repeated measurements of section 15. It works only if search by part of a word has been checked, not assumed: with one query for a piece from the middle of a word that certainly exists.

The reverse case is useful too: the piece gave 1, and the full surname 0. Then the record found holds a different surname with the same piece.

19. To section 3: an unknown parameter returns someone else's data

Besides "nothing found" and "everything there is", a wrongly assembled address has a third outcome. In one archive's API, a query with an invented fond parameter returned code 200 and the files of another fond, and with an invented file parameter — the image of another file. There is no error, the response format is correct: the server does not know such a parameter and returns the first thing at hand. The correct form, taken from the page, turned out to have quite a different syntax [reader's experience].

→ Compare the ownership fields in the response — the fond name, the file number — with what you asked for. If not everything matches, the filter did not work.

Where to get the real addresses: in the browser, open the developer console on the catalogue page and run performance.getEntriesByType('resource').map(r=>r.name) — this lists the addresses the page itself requested [reader's experience]. How to require the same of an agent — Working with agents, section 4.

20. Results pages that overlap each other

The usual paging traps are a skipped or a repeated page. On one catalogue the author met something else: the pages came not as a tape but as overlapping windows, and each next page was 100 records longer than the previous one. For 712 files the page lengths were 100, 200, 300, 400, 312, 212, 112, 12 — 1,648 in total. All the files ended on the fifth page, and the sixth to eighth were a repeat that looked like a short list of real files [reader's experience].

→ Do not add up page lengths. Compare the first records of neighbouring pages — the overlap shows at once. After removing repeats by file number you must get exactly the announced number: for the author, 712 titles, 712 numbers, 712 by the counter.

On short result lists of the same catalogue, paging worked differently [reader's experience]. So check how the pages work on your own result list rather than carrying it over from another query.

21. The server returned less than you asked for and said nothing

In another archive's API, a request for 200 rows ($top=200) and for 500 rows returned exactly 100, while the total counter was correct. A loop that advances by the requested number of rows reads half the file and reports a full pass [reader's experience].

→ Take the paging step from the number of rows returned, not requested.

22. To section 2: "slow" is not yet how the site works

Section 2 is about the instrument changing. The opposite mistake is to take a temporary state of the server for its design. The author wrote down: "10 rows — 6 seconds, 25 — 16, 50 — error 504" — and spent half an hour exporting an inventory 25 rows at a time. A day later the same queries ran in a fraction of a second, 100 rows at a time without errors [reader's experience].

→ A ceiling, as in section 21, is a property of the server; "slow" is a property of the hour. Before writing a limit into your notes on a resource, repeat the measurement at another time.

23. The counter may sit in the tab labels

On one catalogue there was no "found: N" line in the markup, and the author told the agents: count yourselves. Both agents found the counter on the first query — the numbers stood in the tab labels: "Geographic index (1) | Fonds (15) | Inventories (5) | File (712)" [reader's experience]. One query gives the denominator for all sections of the catalogue at once. If a section's tab is missing from the response altogether, that is a zero named by the catalogue itself — in the author's experience more reliable than a zero counted from the results (provided the response is not empty through a failure, section 15).

The lesson: "I did not find the counter" is not the same as "there is no counter". An unchecked statement about the instrument spreads through all further work. How to check such statements in a task for an agent — Working with agents, section 4.

24. Two different 403s: what /robots.txt shows

Section 1 says: a 403 for the whole domain, including /robots.txt, is server protection. The author tells the cases apart by the response to /robots.txt — a service file for search robots that is usually served to everyone [reader's experience]:

Home page /robots.txt What it means
403 403 the whole domain is closed; the refusal came before the address was even parsed. In the log — "blocked". Look for the same material through the institution's open channels: for the author, the archive had a separate official service at another address, open to everyone without a login. This is not a way around a country block
403 404 the server parsed the address and did not find the file, so the domain is open and the pages refuse your program — this is "a refusal to the program specifically" from section 1. For the author the site opened fully in an ordinary browser, and behind it was a fond of half a million images
403 200 service files are served, pages are filtered — the site is alive

→ What to do — as in section 1: check in an ordinary browser, do not circumvent the protection, and on a CAPTCHA or a block by country stop and hand the decision to the human (Access, CAPTCHAs, pace, sections 3 and 4).

25. The index gave a field to the wrong person

An index goes wrong not only in letters but also in whom a field belongs to. In an index of the 1858 revision a family's line was compiled so that the age of 26 stood with the father, while on the image it was his son's age. Searching for the father "aged about 26" in a neighbouring revision would give a false zero, and the family's chronology a false contradiction.

→ Check every index field on which a conclusion rests (age, patronymic, relationship) against the image. Other field-parsing errors — Standard of proof, section 6.

A relationship label refers to a head of household, and the index does not say which one [reader's experience]. A census index gives the column "relation to the head": «сынъ», «невѣстка», «внучка» (son, daughter-in-law, granddaughter). The reader took seven rows with one surname from one village and assembled a household — coherent, with no contradictions. On the image the rows were in three households: three belonged to his man, three to the man's widowed mother (her son, her daughter-in-law, her granddaughter), and the seventh was the daughter of a third brother. The index gives rows in the order of the results, not of the households, and does not say to whom a role refers — so a family assembled this way cannot be refuted without the image. → Mark a household assembled from an index as a conclusion, not a record, and check it on the first image. The same goes for your own tables: a notes column filled in by the order of the result rows looks like data but is a guess.

26. A negative conclusion — with the full list of forms and with candidates who have no patronymic

The conclusion "so-and-so is not in the list" holds exactly as far as the list of forms that was searched. In one round three forms of a patronymic were left out of the list: with "iо", with "е" and the short one in "-овъ" (Лiозоровичъ, Лейзеровичъ, Лейзеровъ), and the fact-checker downgraded the conclusion. In the same round five men whose names began with "Абр…" (Abr…) and who had no patronymic recorded at all could not be dismissed with "none of them has the right patronymic": a person without a patronymic is a candidate, not someone excluded.

→ In a negative conclusion, list every form searched and, separately, the candidates that nothing confirms or excludes.

27. OCR breaks surnames with a variant in brackets

Directories often give a surname variant in brackets: "Surname (Variant)". In the recognised text (OCR) of a directory on archive.org such a line fell apart into single letters with spaces, and a regular expression for the surname returned zero.

→ Read the directory sections for the towns you need from the image, not only from the recognised text. A zero from OCR without a control record from the same section is not a result. Typical recognition errors — Names, surnames, spellings, section 4.

28. The town of a directory entry — by the nearest heading above

In a directory divided into districts and towns, a town's heading appears once and the entries under it run for several pages. An entry at the top of a page belongs to the town whose heading stands above it — sometimes on the previous page. Two rounds assigned the same address-directory entry to different towns; the heading on the previous page settled it.

→ Determine the town of an entry by the nearest heading above, paging back, not by the first heading on the same page.

29. A misreading spreads along the chain of reports

An agent read a patronymic in a record as the expected "Лейзоровичъ" (Leizorovich), while the record said "Лейбовичъ" (Leibovich); it also read the surname as one resembling the surname sought. The error passed through the archive researcher's report, the fact-check, the round summary, the audit and the hypothesis, and only a separate check against the crop removed it: each next role read the previous report, not the frame.

→ A find on which a conclusion rests the coordinator checks against the crop itself (Working with agents, section 10, "Processing the summary"). Do not delete what was corrected in old reports; mark it with a link to the correction, or the error will be restored from the old text (compare "A correction made in one place has not been made", section 7 there). Do not complete a surname you could not read from what you expect: write "Ш[…] (not read)", and rest the identity on other signs — family number, given name, age, note.

30. An extract "about the family" is not a second source for a negative

A certified copy or extract "about the family of so-and-so" copies from the revision only those who were asked about. About a brother missing from the extract it is silent; it does not testify that there was no brother. A negative conclusion needs the list itself, where the person was bound to appear; an extract does not count as a second source. On the independence of confirmations — Standard of proof, section 5.

31. First the structure of the source, then conclusions

A list read without some of its columns gives false zeros. In the sheets of the 1875 military census a column on the right half-sheet holds notes such as "умеръ 18NN года" (died in 18NN) or a place of residence; without it a person looks "missing". Notes on the back of a sheet ("въ г. N" — in the town of N, "умеръ 18NN" — died 18NN) often give the decisive sign.

→ Before reading names, work out from the header how many columns the sheet has and where they continue, and read the back of the sheet.

How to ask AI

For a plain chat, add: "If you can't open a source, say so; mark fonds, villages and dates you name from memory as [from memory, verify]. Answer in English, and give names, places and archive titles in the original script in parentheses." (why). The label (agent with a browser) is for an AI that opens websites itself; the other prompts suit any chat.

  • (agent with a browser) "A query to the database [N] returned zero. Before recording a negative result, answer: did the control record pass by this same route; was the zero repeated once more, after a pause; how many records are in the database in all and how many did the query return; does this search widen the query with synonyms or search literally; was the query address taken from a page of the site or assembled by hand." Check yourself: the control record is certainly in the database; the query address, opened in a browser, gives the same.
  • "The site [N] does not open: [what is visible on the screen]. What diagnosis is it — the site's name is not found, connection refused, certificate, bot protection, a refusal to the program specifically, the resource has changed, a block by country? What checks each? Do not circumvent the protection." Check yourself: open the site in an ordinary browser; pass the CAPTCHA yourself.

Bad → good: "Is [surname] in the database [N]?" (a zero without a control record and spellings proves nothing) → "In the database [N] first find the control record [who is certainly there], then [surname] in all spellings; for each zero, how many records the database has in all."

32. A zero with a filter — repeat without the filter

A year or place filter set in the address bar does not work on some sites and returns an empty result (this happened in Yandex "Search in Archives" in November 2026). Check a filtered zero with the same query without the filter. A zero in a partly indexed collection (FamilySearch, AI-made indexes) means "not in the indexed part", not "never existed".

How to catch a filter that does not work without opening a single card [reader's experience]: compare the announced number of results with and without the filter. On one oblast archive's catalogue the file search accepts a fond-number parameter that the site itself offers. A query filtered by fond 445 returned files of three other fonds (fond 445 did not appear at all) — and exactly the same 42 pages of results as the search without the filter. Equal numbers are the sign that the filter was not applied (section 19, but with a parameter the site itself gave). On the same engine the search parameter on the list-of-fonds page was ignored and returned all 7,160 fonds of the archive: a full listing easily passes for a search result.

33. The site starts returning empty pages in the middle of a run

If after dozens of fast requests the record pages suddenly come back empty or the browser is redirected to another address, a rate limit has kicked in. What you read before that is a result; the rest is "the instrument did not respond". Pause several seconds between requests and do not bypass the protection; finish later or by hand.

34. An index compiled by AI

More and more often an index is compiled not by a volunteer but by a neural network: it reads the scans and writes the names into the database itself (this is how archival.name, for example, works). Such an index distorts names: the card shows one form, the scan another; a surname may be turned into Latin letters, a file title into a machine translation. A search for the "right" spelling then gives zero, and a row that is found may describe the wrong person.

→ Check every hit against the scan the card links to, and quote the scan, not the index. A zero in an AI index is a zero of that index, not of the archive: search in "sounds like" mode and with several spellings, run a control query (section 4), and write in the log "not in the index", not "not in the file". The site usually does not say what share of the files the AI has read — there is no denominator (section 10).

35. A place name is the stem of a common word, and a homonym fills the results

A search for the village Старовичі on the inter-archive portal gave an impressive 12 fonds, 22 inventories, 459 files. The first page showed «Київське товариство старовини і мистецтв», «Товариство охорони пам'яток старовини» (societies of antiquities): the portal searches by stem, and the stem старовин- buried the village [reader's experience].

🔑 This is more dangerous than a zero or than "too many results": the number is large, the results are not empty, and a quick reading declares the place "well represented in the archives" — the error goes into the report with a plus sign.

→ How to catch it: open the first three rows and check whether the place itself is named in them — not "looks like", but is named. → How to fix it: the geographical-index tab, if there is one (the reader found exactly one entry there for this village: the portal knows the place, the general results drown it); another spelling — Russian instead of Ukrainian, case forms, the adjective from the name; narrowing by archive or type of fond. → A zero or a "lot" for such a place is not measured until the query is repeated through the right entry. It happens most with names in ‑ичи, ‑овка, ‑ное. Compare section 8: there the issue is the length of the query, here it is a place name that coincides with an ordinary word.

36. The number in a card's address is an internal id, not the fond number

On one oblast archive's site the address /fonds/445/ opens fond 1411, a volost board of another uezd, while fond 445 lives at /fonds/147/ [reader's experience]. The path looks like a reference and reads like one, but it is a record number in the database. The error is silent: a real card of a real fond opens, just not the right one — and "nothing of ours in fond 445" becomes a false zero that gives no sign of itself. The reader has met this on three different archive engines.

→ Read the reference in the card's heading, where it is written out («Фонд 445 · Опис 1 · Справа 246»), never from the address bar.

37. The image folder is computed from the image number; a wrong folder gives a 404 that looks like "not digitised"

On the same site images live at /static/files/<N>/<ID>.jpg. An executor got a list of IDs from one file, used the folder of the first image — and 11 of 12 addresses gave 404. The conclusion suggested itself: "the file is partly digitised". In fact N = floor(ID / 10000): image 5178114 is in /517/, and 5182874 already in /518/ [reader's experience].

→ If a file path contains a numbered folder, derive it from the id and test it on two ids from different blocks before recording a 404 as absence. This is section 3, but on the path to an image rather than a search parameter — so the error disguises itself as the state of the archive.

38. Images are served by a separate host with its own limits

On Wikimedia Commons on 19.11.2026 upload.wikimedia.org answered 429 with retry-after: 120 to everything: the whole file, partial requests (206), /thumb/, over IPv4 and IPv6, after pauses. In the same minute thumb.wikimedia.org answered 200 on the same /thumb/ paths [reader's experience]. That way the reader downloaded a 185-page file page by page (about 1 MB each) when the whole 175 MB PDF would not download at all; the PDF itself is not served through thumb. (it redirects to upload.).

Two consequences:

  • the advice "take a big file in parts" does not work at such a moment: the limit is on the host, not on the volume, and a partial request is still a request. An executor following the advice will declare the file unavailable;
  • thumbnail widths are not arbitrary: on that host 1280 and 3840 worked, while 2000px gave an error page of 3,292 bytes — a small "file" that is easy to take for an empty page of the file. On another host in October the reader saw the same: 400 for 1024 and 2048 with 1920 alive.

The width the API names is not yet the width of the file. On 21.11.2026, in the compiler's research, the Commons API answered a request for width 1920 with thumbwidth: 1920, while the thumburl link itself said pageN-500px-…: agents read 500-pixel pages and could have brought a false zero. Write the width you need into the path yourself (/pageN-1920px-…), drop the ?utm… tail, and after downloading check the real width of the JPEG: a page narrower than requested is not "no entry" but a reason to download again.

→ Before writing "the site returns 429", try another image host; compare the size of the file you got with the expected one — a three-kilobyte answer to a request for a book page is not a page. How to take files from Commons — skill ukrainian-archives-on-commons.
